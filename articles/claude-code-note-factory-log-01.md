## この記事は何か

Claude Code のクラウドルーチン（定時実行）だけで、note の 500 円有料記事を毎日自動生成して公開する仕組みを作りました。人間がやるのは、生成された原稿を note に貼って公開ボタンを押すことだけです。

6 日間回した結果が、これです。

| 項目 | 値 |
|---|---|
| 公開した有料記事 | 10 本 |
| 1 本あたりの文字数 | 3,800〜4,300 字 |
| スキ合計 | 1 |
| フォロワー | 0 |
| 売上 | 0 円 |

この記事では、仕組みの中身と、なぜ売れなかったかの自己分析を書きます。売れた話ではなく、売れなかった話です。

## 作った仕組み

登場するのは 2 つのルーチンと 2 つの Artifact（Claude Code が公開する Web ページで、小さな DB を持てる）です。

```
毎日 07:00  リサーチ → 企画 → 執筆 → 検品 → 告知文生成 → 「量産キュー」に書き込み
毎週月曜    売上帳とキューの傾向を読んで、導線（プロフィール / 固定ポスト / CTA）の改善案を追記
```

- 量産キュー: 日付ごとに 1 パッケージ。候補テーマ 5 件、採用理由、無料/有料の境界、本文、告知文 10 本、アイキャッチ画像、検品結果が入る
- 売上帳: 売れるたびに人間が手入力する。ルーチンはこれを読んで「売れ筋」を学習する設計
- 検品基準: 24 項目のチェックリストを DB に置き、執筆役が読み、検品役が 1 項目ずつ合否判定して不合格箇所だけ最大 2 周書き直す

検品基準の一部を挙げます。

- 語り手は「私」で、実体験が主軸になっている
- 冒頭は五感を伴う具体的な場面か、一言セリフから始まる
- 無料部分は全体の 28〜35% に収める
- 有料部分の書き出しは「結論から言う」など、すぐ価値を感じられる一文
- 実践パートは番号付きの手順で、各項目に「やること」と「使う場面」がある
- 誤字・異体字を機械検査する（cp932 にない漢字の検出など）

形式面では、かなり整った記事が毎朝 2 本出てきます。

## なぜ売れなかったか

売上 = 閲覧数 × 購入率 × 単価 で見ると、閲覧数がほぼゼロでした。ただ、閲覧があっても買われなかっただろうと思う理由が 4 つあります。

### 1. 有料部分の中身が常識の範囲だった

「時計を視界から外す」「同じ店に 3 回通う」「電話は 10 分だけ聞く」。無料検索で出てくる内容です。予告文で「三つの物差し、七つの手順」と煽っている分、買った人の落胆が大きくなる構造でした。

### 2. 書き手の実在性がゼロだった

匿名アカウントが毎日違う悩みを「私の実体験」として語り、6 日で 10 本並ぶ。プロフィールを見た瞬間に AI 量産だと分かります。この「実体験」は作り話なので、信頼が生まれないどころか、気づいた購入者からの返金要求というリスクも抱えていました。

### 3. 導線がなかった

フォロワー 0 で、note 内検索からの流入はほぼありません。記事の良し悪し以前に読まれていません。

### 4. 検品基準に「買う理由」がなかった

24 項目は文字数比率や区切り位置など形式ばかりで、「読者が持ち帰れる具体物があるか」を問う項目がありませんでした。売れる根拠のない基準で、品質だけを上げ続けていました。

## 気づいたこと

自動化で一番うまく動いたのは「基準をファイルにして、書く役と検品する役を分け、不合格箇所だけ書き直す」ループでした。文体や構成の一貫性は、人間が毎日書くより安定します。

一方で、自動化しても埋まらなかったのは「書き手が本当に持っている一次情報」です。仕組みは文章を作れますが、売る理由は作れませんでした。

## 次にやること

- 商品を、この仕組みそのもの（ルーチン定義、検品基準、プロンプト、検証ログ）に変える
- 告知は Threads API で完全自動化し、反応データをルーチンが読み戻す
- 記事は Zenn の GitHub 連携で push だけで公開する
- 撤退条件を先に決める。2 週間で購入 0 なら型を変える

検証ログは続けます。数字は失敗も含めてそのまま出します。
